# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
go build -o taskboard .
./taskboard -config taskboard.json   # taskboard.json is gitignored; start from config.example.json
go vet ./...
go test ./...
go test -run TestBuildTasks ./...    # single test
```

Single `main` package (Go 1.22, uses `ServeMux` method/path patterns). Dependencies are limited to `coder/websocket` and `creack/pty` (browser terminal) and `go-pkcs12` (client certificate files); xterm.js is vendored in `static/` and embedded. All tests are in `taskboard_test.go` and use `testConfig(t)`; they never shell out, so they run without `gh`/`acli`. The binary requires `acli`, `gh` and `git` on PATH at startup.

## Architecture

A local dashboard for multitasking across many parallel coding-agent sessions. It joins Jira tickets, GitHub PRs, git worktrees, plan files and tmux sessions on the ticket key; Jira is the only tracker today, but others (e.g. GitHub issues) may be added, so avoid baking in Jira-only assumptions where it's cheap. README.md documents user-facing behaviour and config; keep it in sync when behaviour changes.

Data flow:

1. **Sources** shell out via `runCmd` (`local.go`): `jira.go` (`acli jira workitem search/view`), `github.go` (`gh pr list`, `gh search prs`), `local.go` (`git worktree list`, plan files in each worktree's `plans_dir`, `tmux list-windows`). Keys are extracted with `Config.findKey` (regex built from `project_keys` in `config.go`).
2. **`Board.refresh`** (`board.go`) runs the sources concurrently, then looks up any keys seen in PRs/worktrees/sessions but not returned by the JQL (`unknownKeys` → `jiraGet`), and fills Jira updated dates and epic parents (`fillJiraDetails`; acli search can't return `updated` or `parent`, so it's one `view` per issue, cached and re-fetched only for issues a search reports as changed). It also lists each open epic's children (`epicChildren`, one search per epic) into `fetched.children`. Board keeps caches for done/missing issues (24h TTL). Source failures become strings in `Snapshot.Errors` rather than aborting the refresh.
3. **`buildTasks`** (`tasks.go`) is a pure function from `sources` to sorted `[]Task`. Plans attach only to tasks already found via another source. PRs without a key become `NoTicket` tasks keyed `repo#number`. `buildEpics` then groups each open epic task with its children (from task parents and `fetched.children`) into `Snapshot.Epics`; `taskGroup` keeps an epic with no work of its own out of the stage sections.
4. **Stage logic** (`progressStage`/`stageFor` in `tasks.go`): the `Stage` constants are declared in display-priority order and sorting depends on that order. `stageInfo` maps each stage to its label, tone, group and track station. Done tasks with a worktree or session become `StageCleanup`; Done tasks outside the `done_days` window are dropped.
5. **Session actions** (`session.go`) are the only code that changes anything: start (worktree + tmux window), stop and clean-up. `startPlan` and `removalCheck` are pure and tested; the git/tmux calls around them are not. Actions re-read sessions and worktrees with `liveTask` because the snapshot can be minutes old, run on their own context so a page reload can't abort a half-made worktree, and call `Board.LocalChanged`, which republishes the snapshot at once from freshly read worktrees, plans and windows plus the last refresh's Jira/GitHub data (`fetched`, never modified once stored), then calls `Invalidate` (unlike `Refresh`, it isn't dropped during a running refresh). A refresh that started before an action re-reads local state before publishing (`localGen`), so it can't bring back what the action removed. Clean-up must never remove a main checkout (`Worktree.Main`) and keeps any branch with unpushed commits, even when forced. Reviews work the same way on `PRLink`s: `attachReviews` matches worktrees and windows named `<checkout>-pr<N>` (no ticket key, so they never become tasks) and returns leftovers for PRs no longer listed; their routes are under `/review/`. Which buttons a row shows is decided in Go (`taskControls`/`prControls`), not in the templates. Attaching (Open session, the copied command) goes through a linked tmux session marked `@taskboard`, so terminals don't move each other's current window; `listWindows` skips marked sessions, and each refresh sweeps never-attached ones (`staleLinked`).
6. **Server** (`server.go`) renders the snapshot with embedded `html/template`s (`templates/*.html`; `tokens`, `updated`, `prrow` are partials; `sectionOrder` sets the order of the sections). Reviews/Other repos PR sections (`PRLink`) are separate from tasks and not joined on Jira keys; `splitPRLinks` limits Other repos to the owners in `github.organizations` (empty means all); review sessions are matched by worktree/window name instead.

Config: the settings page saves the config file (`SaveConfig`) and swaps it into the running board (`Board.SetConfig`). Read it through `Board.Config()` once per refresh or request and treat it as immutable; only `listen` is fixed at startup. Settings with a default (`agent`, `jql`, `tmuxSession`, `plansDir`, `tlsDir`) stay empty in `Config` and are resolved by accessor methods at use, never filled in by `validate`, so the settings page shows each default as its field's placeholder and saving never writes it to the file.

Highlights (`highlights.go`): the set of highlighted IDs (task key, or `PRLink.ID()` for PR rows) lives in `taskboard-highlights.json` next to the config. `/version` returns it so open pages update in place; it is deliberately not part of `Snapshot.Version`, so highlighting never forces a reload.

Polling: `Board.Run` polls every `poll_interval` while the page was viewed in the last 15 minutes (`idleAfter`), otherwise `idle_poll_interval`; a view after idling wakes it immediately via `Board.Viewed`. The page polls `GET /version` and reloads only when `Snapshot.Version` (hash of tasks/PRs/errors, excluding `Updated`) changes.

Security: `accessOf` classifies each request. **local** is a loopback client on the plain `listen` address (no auth); **remote** is a client on `tls_listen` presenting a certificate from taskboard's CA (`certs.go`: mutual TLS, `revoked_certs` checked at the handshake and again per request); anything else is a **viewer** and can only read. Native terminals (`POST /attach`, `/review/attach`, `open=terminal` on start) run `attach_command` on this machine and are local only. Everything else that acts (`POST /start|stop|cleanup/{key}`, `/review/{start,stop,cleanup}/{name}`, `/settings`, `/highlight`, the browser terminal) needs local or remote. Every POST also needs the `X-Taskboard: 1` header, which forces a CORS preflight that is never answered; client certificates are ambient credentials like cookies, so this matters on the TLS listener too. The terminal WebSocket (`terminal.go`) relies on `websocket.Accept` rejecting cross-origin upgrades instead, and only attaches to a known task's or review's window. `checkHost` rejects hostnames not in `allowed_hosts` on the plain listener (DNS-rebinding guard); TLS requests skip it, since the browser validates the server certificate's names. Session actions take a per-key in-flight claim (423 while one runs). Preserve these when touching the server.
